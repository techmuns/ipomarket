## 2. Production target decision

### 2.1 Options considered

- **A** — Update `ipo-financials.json` only. Cheapest; produces an "orphan" IPO with no row in `ipo-documents.json`. The UI may render OnEMI with "no documents available" — misleading, because the BSE-hosted RHP URL is already known to the curated seed.
- **B (RECOMMENDED)** — Update `ipo-financials.json` AND a minimal new row in `ipo-documents.json` linking the OnEMI RHP. No change to existing IPO documents rows. No change to `ipo-narrative.json`. No change to `ipo-source-audit.json`. No change to `ipo-master.json`.
- **C** — Update all four production snapshots including `ipo-source-audit.json`. Most consistent — but `ipo-source-audit.json` is auto-generated by `scripts/ingest/source-audit.ts` from probe results (NSE master record fields, not financial periods), so adding OnEMI financial-period entries doesn't fit the existing per-field-provenance shape. Out of scope for §8's "no `scripts/ingest/*` changes" guardrail.

### 2.2 Recommendation: Option B

Rationale:
- Avoids the orphan-IPO inconsistency between financials and documents.
- Minimal addition: ONE new ipo_id entry in `ipo-documents.json` (just `docs[]` carrying the BSE RHP URL + `state: 'live'`); existing 10 IPO rows are byte-identical.
- The §X.1 "no `ipo-documents.json` mutation" rule from Phase 5A.x was about preventing accidental side-effects during PDF parser feasibility — not about preventing intentional, gate-approved promotion. Phase 5B.1 IS the explicit promotion gate; mutating `ipo-documents.json` for the new IPO row is in-scope.
- `ipo-source-audit.json` (Option C) stays untouched because its per-field-provenance shape doesn't fit financial-period audit. The Phase 5B audit chain (staging JSON → `ipo-pdf-extraction-audit.json.normalization` → ipo_id linkage) already provides the provenance trail.

This is a deliberate, gate-approved loosening of the §X.1 rule for Phase 5B.1 only, with the §7 safe-merge rules guarding against unintended side-effects.

## 7. Safe-merge rules (binding)

The Phase 5B.1 promoter MUST:

1. **Read existing snapshots first** via the canonical loader (`readJsonOrNull` from `scripts/ingest/lib/safeWrite.ts`). Treat missing/malformed file as a HARD STOP (do NOT create a fresh file from scratch — too risky).
2. **Update ONLY the OnEMI row**. Use `delete by_ipo['onemi-technology-solutions']` then `by_ipo['onemi-technology-solutions'] = newRow` so any prior partial entry is overwritten cleanly. Do NOT touch any other ipo_id key.
3. **Preserve all existing manual rows** byte-identically. After the write, `Object.keys(by_ipo).filter(k => k !== 'onemi-technology-solutions')` must produce the same list as before, with same content.
4. **Do not wipe missing fields**. `ebitda_cr`, `debt_cr`, `eps` are written as explicit `null`, not omitted. `derived.*` written as explicit nulls.
5. **Atomic writes** via `safeWriteJson` (`.tmp` + rename) — already used by all existing snapshot writers.
6. **Idempotent output**: running the promoter twice in succession against the same staging snapshot must produce identical bytes.
7. **Source-audit entry**: skipped per §2 / §6 — `ipo-source-audit.json` not touched in Phase 5B.1.
8. **No UI changes** unless absolutely required (e.g. a null-tolerance shim) AND separately approved before the implementation pass starts.
9. **Update `generated_at_utc`** on both `ipo-financials.json` and `ipo-documents.json` to the current ISO timestamp (matching the existing convention).
10. **Pre-flight verification**: the promoter must read the OnEMI staging snapshot AND verify (a) `manual_review_required: false`, (b) all 4 required-3 keys present at HIGH confidence (revenue/pat/total_assets), (c) all 4 periods detected at HIGH confidence, (d) `unit_detected.confidence !== 'low'`. If any check fails, promotion HALTS without writing.

- Touch any workflow file under `.github/workflows/*` (binding — the promoter is invoked locally; existing CI workflows including `pdf-parse.yml` are untouched)
- Commit PDF binaries or full-text dumps
- Extend `src/types/source.ts`
- Extend `src/types/ipo.ts` with new required fields (additive optional only — and only if strictly necessary)

### 8.2 Phase 5B.1 IS allowed to

- Add ONE new ipo_id entry to `ipo-financials.json` (OnEMI, `state: 'live'`)
- Add ONE new ipo_id entry to `ipo-documents.json` (the minimal OnEMI RHP linkage per §3.3) — this is the §X.1 loosening explicitly approved in this plan
- Create a new promoter script under `scripts/pdf/promote/` (e.g. `scripts/pdf/promote/onemi.ts` — single-purpose, OnEMI-only)
- Write `phase-5B1-status.md` after the implementation run

### 8.3 UI-visibility caveat (binding)

Phase 5B.1 writes financial data + a documents-row link, but it does **NOT** add OnEMI to `src/data/snapshots/ipo-master.json` — the dashboard's primary IPO master record (which feeds the IPO selector, the detail-page route, and the cross-snapshot joins for narrative / listing-performance / source-audit / sebi-pipeline).

**Consequence**: after Phase 5B.1 lands, OnEMI's financial + documents data will be present in production snapshots but may **NOT be visible** in the dashboard's IPO selector or detail page — depending on whether the UI iterates `ipo-master.json` (selector-driven) or iterates `ipo-financials.json` keys (financials-driven) to render the IPO list.

This is acknowledged-and-deferred, not a defect. The Phase 5B.1 `phase-5B1-status.md` MUST include an explicit operator-facing question at the end: **"Plan a separate Phase 5B.X master/detail linkage pass to add OnEMI to `ipo-master.json` (and any other selector-feeding snapshot) so the dashboard actually surfaces the new row — yes / hold / no?"** The operator answers this question separately; no master-linkage work is started without explicit further approval.
